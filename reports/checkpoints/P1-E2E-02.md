# P1-E2E-02 — Failure paths và safe recovery

## Stage này giải quyết vấn đề gì?

Xác nhận lỗi bị phát hiện sớm, có thông báo hành động được và không làm hỏng canonical data. Một pipeline chỉ có happy path giống xe chỉ thử chạy tiến mà chưa thử phanh.

## Trước stage này project thiếu gì?

DQ controlled failure và loader validation đã có riêng lẻ, nhưng chưa được tổng hợp thành evidence E2E cho hành vi lỗi, downstream và recovery.

## Runtime evidence

| Scenario an toàn | Kết quả quan sát | Tác động / recovery |
|---|---|---|
| Missing SUSEP path | Loader exit 1: `Không tìm thấy raw SUSEP: ..._missing_susep_for_controlled_test.csv` | Không kết nối/ghi DB; sửa path hoặc mount file đúng rồi rerun. |
| Invalid SUSEP header | Loader exit 1: `Header SUSEP không khớp contract` | Chặn trước ingestion; không nhận file có 7 cột thay vì contract 8 cột. |
| SQL unavailable simulation | Airflow-container loader với `--server sqlserver,1434` exit 1: `Login timeout expired` | Không có DML trước connect; khôi phục service/host/port rồi rerun. |
| Duplicate source-version rerun | Loader trả `SKIPPED`, batch `0EDEB285-DB67-4159-A6D5-FE85F00F085A`, accepted 8.338.214 | Không duplicate staging/fact; đây là recovery an toàn cho rerun. |
| Track-A DQ controlled invalid input | SQL procedure tạo `CONTROLLED_INVALID_INPUT=FAIL`, rồi `THROW`; canonical count không đổi | Bỏ injection và chạy production DQ để recovery. |
| Airflow Track-A DQ failure | Run `0d2f017a-1f52-46b2-9671-2f1e3d95f488`: DQ `failed`, Track-A consumer `upstream_failed`, Track-B consumer `success` | Xem log/rule, sửa nguyên nhân rồi trigger run mới; không rerun consumer trực tiếp. |

## Agent đã sửa những file nào?

- Không sửa raw, source, fact hoặc model để tạo lỗi.
- Tạo fixture schema invalid tạm thời ngoài raw, chạy test rồi xóa fixture.
- `dags/insurance_dwh_pipeline.py` được sửa ở P1-ORCH-02 để SQL `THROW` không thành false success.
- Checkpoint này lưu evidence và recovery playbook.

## Data/code đi qua đâu?

File/source validation xảy ra trước batch insert. Kết nối SQL phải thành công trước staging DML. Sau DWH/reconciliation, DQ là gate trước consumer. Airflow dùng task dependency để chặn đúng nhánh. Mỗi lớp là một cửa kiểm soát khác nhau.

## Owner cần hiểu khái niệm gì?

- **Fail fast:** từ chối file/header sai trước khi tạo batch dở dang.
- **Actionable error:** lỗi nói người vận hành cần kiểm tra path, header, port hoặc rule nào.
- **Safe recovery:** rerun maintained entry point sau khi sửa nguyên nhân, không sửa tay count hay bypass DQ.

## Owner tự kiểm tra thế nào?

Không tạo/sửa CSV trong `data/raw`. Thay vào đó, truyền một path không tồn tại vào loader; dùng một fixture temporary ngoài raw cho header test; và trigger Airflow với controlled conf được ghi trong `P1-ORCH-02.md`.

## Điều gì có thể nhìn đúng nhưng thực ra sai?

Một task có log DQ `FAIL` vẫn có thể hiện `success` nếu client không consume result set chứa SQL `THROW`. Đây là lỗi đã phát hiện và sửa: DQ operator nay drain result set. Không nên simulate outage bằng cách stop SQL Server hoặc rename ML artifact đang là canonical evidence khi có cách port/path/in-memory test an toàn hơn.

## Stage verdict

**PASS.** Các lỗi được phát hiện ở boundary đúng, thông báo đủ hành động, canonical raw/data không bị hỏng và Airflow block đúng downstream.
